# CDC with PostgreSQL

## CDC(Change Data Capture)

CDC 란 Change Data Capture 의 약자로 데이터베이스에서 발생하는 변경 사항(INSERT, UPDATE, DELETE 등)을 실시간 또는 준 실시간으로 감지하고, 이를 외부 시스템에 전달하는 기술이다.

주로 데이터베이스간의 동기화, MSA 간의 통합 등에 사용되며, 전체 데이터를 주기적으로 읽지 않고 변경된 데이터만 효율적으로 추출할 수 있도록 해준다.

## PostgreSQL Setting for CDC

PostgreSQL에서 CDC를 구현하기 위해서는 사전 설정이 반드시 필요하다. 우선 postgresql.conf 파일을 수정해야 하는데, 반드시 수정해야하는 파라미터는 `wal_level` 파라미터이다.

`wal_level` 파라미터에 대해 이야기하기 전에 WAL(Write Ahead Log)를 먼저 알아야 한다. WAL 란 Write Ahead Log의 약자로 PostgreSQL이 데이터베이스의 신뢰성을 보장하기 위해서 데이터를 기록하기 전에 WAL 이라는 로그 파일에 먼저 변경사항을 기록하게 된다. 이렇게 WAL file에 변경사항을 먼저 기록함으로써 시스템 장애 시 이 로그 데이터를 기반으로 복구를 할 수 있게된다.

그렇다면 `wal_level` 파라미터는 무엇일까? `wal_level` 파라미터는 Write Ahead Log에 얼마나 많은 정보를 기입할지에 관한 파라미터이다. 즉, WAL File에 어느 정도의 정보를 얼마나 자세히 남길지 설정하는 파라미터이다.
이 파라미터는 DB 서버가 시작할 때 설정할 수 있다.(DB가 기동중이라면 운영 DB 서버여도 반드시 재기동이 필요하다.)

`wal_level` 에 설정 가능한 값은 다음과 같다.
- `minimal` : 최소한의 WAL만 기록한다. 시스템 복구가 가능하지만 복제는 불가능한 정도만 기록하게 된다.
- `replica` : 복제를 위한 WAL 까지 기록한다. Standby 서버에서 읽기가 가능해서 복제도 가능해진다. 이 때, 복제는 전체 데이터를 복제하는 것이지 필터링을 하거나 몇 개의 특정 데이터만 복제가 불가능하다.
- `logical` : replica 수준 + 논리적 복제를 위한 정보를 기록한다. 논리적 복제는 테이블 수준으로 복제하거나 변경사항을 분석해서 다른 시스템(Kafka 등)으로 보내는 것을 의미한다. replica와 다르게 필터링 하여 특정 데이터만 보낼 수 있다는 점이 특징이다.

그렇다면 왜 CDC를 PostgreSQL에서 수행하려면 `wal_level` 을 변경해야 할까? CDC의 특성상 특정 레코드나 컬럼이 변경되면 변경사항을 감지해서 이벤트를 발행하는 구조이다. 하지만 PostgreSQL의 기본 `wal_level` 값은 `replica` 로써 특정 데이터(테이블 수준)의 복제가 불가능하다는 점이다. 이 때문에 CDC 를 수행하려면 `wal_level` 을 `logical` 수준으로 변경해야 한다.

`wal_level` 뿐만 아니라 유연하게 CDC를 할 수 있는 여러가지 파라미터가 있는데 이는 생략하도록 한다. 궁금하면 구글에 검색해보면 된다.
## Replication Slot

`wal_level` 을 설정했으니 이제 논리적 복제가 가능해질까? 결론부터 말하면 반은 맞고 반은 틀리다. PostgreSQL 9.4 이전 버전에서는 논리적 복제를 하는 Slave 서버(데이터베이스, Kafka 등)와의 연결이 끊어지면, Master Server가 Slave Server의 복제 상태를 알 수 없기 때문에 Slave Server가 복구되기 전에 Slave Server가 아직 받지 못한 WAL FILE을 삭제해버린다는 문제점이 존재하였다. 

이러한 문제를 해결하기 위한 방법으로는 `wal_keep_segments` 파라미터를 조정하여서 WAL FILE의 보존주기를 설정할 수 있지만 Slave Server가 언제 복구될지 모르는 순간이기 때문에 조정을 하는것도 예측으로 했을 뿐이었다.

따라서 PostgreSQL 9.4 버전 이후부터는 Replication Slot 이라는 개념이 도입되었다. Replication Slot은 Slave Server 와의 연결이 끊어져도 Replication에 필요한 WAL FILE이 Master Server에 유지되도록 하는 기능을 의미한다. 즉, Slave Server 중 하나의 서버라도 WAL FILE의 데이터를 수신하지 않았다면 WAL FILE 내의 그 데이터는 삭제되지 않는다는 것이다.

이렇게 Replication Slot 덕분에 사용자는 논리적 복제 시 데이터 손실에 대한 리스크를 없애게 되었다.

### Replication Slot with WAL file size

그렇다면 WAL File의 용량은 어떻게 관리되는 것일까? WAL File은 기본적으로 Slave Server가 WAL File에 대한 데이터를 수신하면 VACUUM 에 의해서 주기적으로 삭제된다. 데이터의 변경이 많아서 WAL File 이 많아진다 하더라도 `max_wal_size` 를 설정하여 조절할 수 있는데, WAL File이 가질 수 있는 최대 용량이다. 이 크기를 넘어가려고 하면 WAL File을 재사용하여 주어진 용량 내에서 유지할 수 있도록 하는 것이다.

그렇다면 Slave Server가 다운된 상태에서 `max_wal_size` 가 넘어가면 WAL File이 지워져서 Slave Server와의 정합성 차이가 생기는 것이 아닐까? 그렇지 않다. `max_wal_size` 가 넘어가더라도 Slave Server가 데이터를 수신하지 않는다면 `max_wal_size` 파라미터를 무시하고 Slave Server가 수신할 때까지 영원히 무시하게 된다.

그러면 Slave Server가 다운된 상태로 오래있는다면 스토리지가 꽉차서 DB가 다운될 수 있는거 아닌가? 그렇다. 그렇기 때문에 WAL File의 용량이 넘어가는지, 또는 Slave Server가 지속적으로 데이터를 수신하는 지 모니터링을 해줘야한다. 그렇지 않는다면 WAL File이 몇 TB 이상 쌓여서 DB의 스토리지가 꽉차서 DB가 자동으로 다운될 수가 있다.

## Publication

마지막으로 Publication 을 설정하면 PostgreSQL에서의 CDC 세팅은 완료된다. Publication 이란 logical replication(논리 복제)에서 사용할 대상 테이블 목록을 정의한 Object를 의미한다.

```sql
CREATE PUBLICATION이름 [ FOR TABLE [ ONLY ]테이블이름 [ * ] [, ...] | FOR ALL TABLES ] [ WITH (발행_매개변수 [=값] [, ... ] ) ]
```

어떤 테이블을 대상으로 복제를 할 지, 어떤 DML 작업에 대한 변경사항을 발행할 지를 지정하는 것이다. 어떤 DML 작업에 대한 변경사항을 발행할 지는 WITH 구문에 작성하면 된다. WITH 구문을 지정하지 않는다면 기본적으로 INSERT, UPDATE, DELETE, TRUNCATE 작업에 대한 변경사항을 모두 발행한다.

t_ticket 테이블에 대한 INSERT, UPDATE, DELETE, TRUNCATE 작업에 대한 변경사항을 발행하는 Publication을 생성한 것이다.

```sql
CREATE PUBLICATION t_ticket_publication FOR TABLE public.t_ticket;
```

이렇게 Publication을 생성했다면 이제는 수신받을 Slave Server(외부 DB, Kafka Connect 등)에 대한 세팅을 하면 된다.
